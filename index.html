    02 — Problem choice

    Why this problem

    It is the only one of the three with a real input pack and an output you can check against a stated definition. The pain is concrete and recurring: an editor watches 50 episodes of every show by hand, and Kuku ships a show a week, so the cost grows with the catalogue while the editor’s hours don’t. It is also narrow enough to finish — find moments and boundaries, not cut video.

    03 — Where the brief was silent

    Assumptions I made

    1. Screenplay timestamps match the rendered video 1:1.
    2. 20–60s inclusive; the hook must land in the first 3 seconds.
    3. Clips cut on beat boundaries, never mid-line.
    4. “Makes sense on its own” is judged on the clip alone, not the series.
    5. Multi-segment promos allowed; a continuous stretch preferred.
    6. Spoiler risk rises with episode number — a proxy, since there is no audience data.

    04 — Approach

    How it works

    parsecode
    candidatescode
    judgeAI
    rankcode
    rendercode

    The one design rule: the model never emits a timestamp.

    The parser turns every scene, line and action into a beat with an id and exact times — 50 episodes, 3,727 beats, 0 parse warnings. The LLM only selects beat ids and writes prose; code maps ids back to times. A hallucinated timestamp is impossible by construction.

    Code gives the model [E01.B076] “I am the daughter they choose.”
    →
    Code maps it back E01.B076 = 01:51.10

    Validation rejects any id not in the candidate, or any illegal duration — it fired 8 times in 200, each logged in run_report.json.

    What stayed deterministic, and what was handed to judgement
    Kept as codeGiven to the AI
    Parsing, timestamps, beat idsIs this actually a hook?
    20–60s limits, boundary snappingDoes it cut on something unresolved?
    Candidate generation and pruningWould a stranger follow it?
    Ranking, diversity, dedupeThe hook / cliffhanger / why lines

    Heuristics cut 3,727 beats to 200 candidates, 4 per episode. That is cost control, not judgement: it fixes the per-show bill before the run starts. Ranking is code so a human can read and argue with the policy instead of finding it buried in a prompt. The model tightened the boundaries on 118 of 200 candidates, so the beat-id mechanism is doing real work, not being rubber-stamped.

    The output is a ranked shortlist of 20 clips for an editor to approve — not a publishing decision.

    07 — Honest failures

    Where it picks badly

    The soft-ending problem is the one I would fix first — and I know how.

    Top failure · 6 of 30

    Soft endings

    The model scores cliffhanger 4/5 and the clip still cuts on a resolution — #3 ends on a flirt. Absolute 1–5 scoring is the cause: standalone has sd 0.66 and not one clip in 200 scored below 2.

    Over-correction

    Slightly too harsh at the gate

    4 of 12 sampled rejects were clips I would have posted — including one ending on the single word “Arsenic.”

    Dead signal

    Spoiler risk does nothing

    198 of 200 clips scored 1 or 2, so the −0.10 spoiler weight barely moves the ranking. Episode position is a weak proxy.

    Structural ceiling

    It reads prose, not frames

    A striking image with no dialogue or action verb is systematically underrated. This is a limit of any text-only approach, not a bug that can be tuned away. Stitched promos likewise ship flagged stitch_unverified_continuity — the tool cannot confirm two shots cut together cleanly.

    08 — Scale

    Cost at real volume

    200 calls per show, roughly 230k tokens. Two free-tier limits bind: 15 requests/minute, which sets the ~16 minute wall time, and 500 requests/day, which caps you at ~2.5 shows per day. I hit the daily wall during testing — it is the limit that would actually bite a team shipping weekly. A paid tier removes both: under a minute, cents per show.

    Cost scales with --per-episode, not episode length, so a new show’s budget is known before it runs. --reuse-judgements re-ranks a past run for free — which is how the ranking was tuned without spending quota. Swapping the model is a flag (--provider gemini|openai|groq|anthropic), or --no-llm to run with no key at all.

    09 — Tooling

    Where the AI got it wrong

    Built with Claude (Claude Code); Gemini 3.1 Flash Lite judges inside the tool. Four real errors, all caught by tests or measurement:

    1. Claude used a retired model id (gemini-2.0-flash, 404) — the API had to tell us. Fixed by listing models from the API instead of trusting memory.
    2. Claude’s windowing assumed beats were time-ordered. They are not: CAMERA and DIALOGUE are parallel tracks that step backwards up to 1.0s in 8 places. Caught only because a test asserted the invariant.
    3. My own lexicon scored a cosy scene as violence — crack(ing) matched “crackling hearth fire” and fires? matched “hearth fire”, ranking a bandaging scene 19th.
    4. Bigger model, same answer, 100× the time. A reasoning-grade Gemini took ~245s per judgement versus ~2.5s for flash-lite, returning identical scores. Separately, one run hung two hours on 2.2 seconds of CPU — the SDK has no default HTTP timeout.

    10 — Next

    What I’d do next

    • Replace absolute 1–5 scoring with pairwise comparison — which is what both the compressed distributions and the soft-ending failure point to.
    • Learn the ranking weights from real watch-through data instead of hand-setting them.
    • Sample keyframes for the top candidates to close the text-only gap.
