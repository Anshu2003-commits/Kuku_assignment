Read the script,
don’t watch the show.

Today an editor sits through all 50 episodes to pick promo moments, and Kuku adds a show every week. Every episode already arrives as a timestamped screenplay, so I let software read it instead and hand the editor a ranked list of 20 clips with exact in/out times. The editor’s job shrinks to approving.

E Why I picked this problem
  • Real input. It was the only option with an actual data pack, so results can be checked, not imagined.
  • Recurring pain. A new show every week means the saving compounds; it is not a one-off.
  • A testable definition. The brief says what a promo is (length, hook, open ending), so I could score against it.

I Where it still picks badly
  • 6/30Soft endings. The judge gives a 4/5 cliffhanger to clips that end on a resolution, e.g. a flirt. Absolute 1–5 scores are the weak spot.
  • 4/12Too strict at the gate. Some rejects were postable, one ending on the single word “Arsenic.”
  • 198Spoiler score barely varies. 198 of 200 clips got 1 or 2, so it hardly moves the ranking.
  • —Reads words, not pictures. A striking silent shot is underrated. Any text-only method shares this limit.

L Gaps in the brief I had to fill
  1. Script times match the cut video 1:1.
  2. 20 and 60 s are both allowed.
  3. Clips start and end on whole beats.
  4. “Makes sense alone” is judged on the clip only.
  5. Joining two segments is allowed; one stretch preferred.
  6. Spoiler risk grows with episode number.
M Bugs my AI assistants introduced
  • Retired model id → 404. Now I list models from the API, not from memory.
  • “Beats are always in time order.” False in 8 places; a parser test caught it.
  • Hearth fire read as violence. Hand labels caught it; fixed in G.
  • A run hung for 2 hours. The SDK has no default timeout; I added one.
N What I’d build next
  • Pairwise judging instead of lone 1–5 scores; it targets both failure modes.
  • Learned weights from real watch-through data.
  • Keyframes for top picks, to catch silent moments.
